## 0. How to use this file

* Use it as the single context for CV, LinkedIn, GitHub, project, learning, certification, job-search and geography decisions for the profile in §2. **§1–21 = Layer 1 (employer demand); §22–25 = Layers 2–3 (observed candidate supply, demand × supply); §26 = visual decision layer (BQ01–BQ45) and the open-question register.**
* Every number is copied from `outputs/tables/` (ids in brackets). In the private repository each row can be traced to a source record via `data/processed/postings_dedup.jsonl` (`posting_uid`, `source_url`; on disk, untracked from git since D-026); in the public repository only the aggregated tables exist (§21). Machine-readable versions: `outputs/{market_summary,skills,roles,locations,languages,salaries,career_paths,jobbarometer,adjacent_demand,clusters,data_quality}.json`.
* Vocabulary: **share** = share of postings that *mention* an item (not "require"); **core postings** = 720 deduplicated postings whose title falls into eight data role families; **719** = those with a description (denominator of all text-derived shares); **Styria** = Bundesland Steiermark (n = 58 by the location flag incl. multi-site ads; 54 by primary state, T03a — quote a count and its share on the same basis, D-027); **Graz area** = Graz plus commuting municipalities (config/geo.json, n = 52).
* Robustness: *robust* = n ≥ 200, same direction in AMS and board/LinkedIn data, CI clear; *tentative* = otherwise. **Every Styria-only number is tentative (n = 58).** Always quote Styrian figures as counts ("8 of 58"), not only as percentages.
* Calibration: this dataset measures what advertisements *say*. It does not measure hiring, interviews, negotiability of stated requirements, or pay. Use "postings mention", "ads state", "advertised floor" — never "employers hire", "jobs per year", "salary".

## 11b. Seasonality (S01–S06, seasonality.json, docs/seasonality.md)

External series, added 2026-09-16: Eurostat Job Vacancy Statistics `jvs_q_nace2` (Statistik Austria Offene-Stellen-Erhebung), Austria, quarterly, non-seasonally-adjusted, 2009-Q1…2025-Q4, NACE aggregates only. **Our own snapshot cannot measure seasonality** (one day; 52 % of core ads first published in the collection month, 90 % within 90 days = survival decay, S05) and no seasonal claim may be made from it.
Seasonal index (1.00 = average quarter; ratio to own-year mean, cross-checked with a 2×4 centred moving average): market services G-N Q1 1.007 / Q2 0.979 / **Q3 1.038** / Q4 0.976; industry B-F **Q1 1.072** / Q2 0.993 / Q3 0.978 / Q4 0.957; public O-S Q1 0.989 / **Q2 1.058** / Q3 1.023 / Q4 0.930; total B-S Q1 1.014 / Q2 0.995 / Q3 1.022 / Q4 0.970.
**Robust:** Q4 is the weakest quarter in every aggregate, both methods, all samples, and the modal weakest quarter in 8–10 of 16–17 years. **Q1** is the most frequent annual peak in industry and in the total economy. **Confounded:** the G-N Q3 peak includes tourism/retail (NACE I and G sit inside G-N); it is not evidence about ICT or data roles. **Amplitude:** best-vs-worst quarter 5–14 % versus best-vs-worst year 255–567 % (19–49×) — the cycle dominates the calendar.
Advising rule: never recommend timing applications by month on this evidence; Oct–Dec is the defensible build/study block and January the defensible readiness target. No occupation grain, no regional grain (Styria not separable).

## 18. Methodology in one paragraph (docs/methodology.md)

Five sources queried Austria-wide with 45 title keywords on one day (no login/CAPTCHA/paywall bypass; StepStone/Indeed/hokify blocked and excluded); raw responses stored verbatim (private); one row per source posting; rule-based title normalisation into families (config/role_taxonomy.json, precision measured in Q03c); geography from explicit fields/NUTS-3/text; salary from structured fields or text near salary words (monthly × 14, plausibility bounds, minimum vs range labelled); language requirements from context windows; degree wording in four strengths; skills from a ~260-item bilingual controlled vocabulary; union-find dedupe; statistics on canonical core rows with Wilson CIs; k-means/NMF as descriptive archetypes; AMS JobBarometer parsed from HTML for yearly counts; decision matrix = transparent weighted sum with sensitivity (docs/decision-framework.md).

## 19. Source coverage & confidence (docs/data-quality.md, docs/limitations.md)

Robust: family/title ranking; top-10 technology ranking and levels; German/English split; certification and PhD rarity; Vienna dominance; advertised floors by family/seniority; JobBarometer trend and Styria share. Tentative: every Styria-only figure (n 58); marketing/product analytics profiles (n ≤ 24); remote-day norms (6 ads); anything about StepStone-only employers; business_analysis and data_governance composition (precision 76 % / 64 % strict). Not measured: hiring outcomes, negotiability of language requirements, extraction recall, actual pay.

## 20. Limitations to keep in mind when advising

One-day stock, not yearly flow; title-based inclusion misses data-heavy non-data titles (§12); 19 % of core postings have no named employer; salary = legal minimum; German "not mentioned" in German-written ads usually implies German; "C1-equivalent" mostly means "sehr gut"; small Styrian cells; posting ≠ vacancy ≠ hire; no causal claims about language or any skill.

## 22. Layer 2 definitions, datasets, schemas, limits

* **Unit.** A public GitHub account with an Austrian location string (not a person, not the workforce). Populations: **P_all** 9,409 · **P_data** 1,818 (bio-declared T1 or repo-evidenced T2) · **P_T1** 872 (bio declares a core data role; the only rows with a family) · projects 6,677 (documented 3,959; substantive 2,605). Frames: A bio-keyword search, **B complete Styrian population (the only complete region)**, C base-rate sample elsewhere (Vienna = lower bound). Base rate in frames B/C: ≈ 11–12 % of Austrian accounts with a repository carry a data signal, ≈ 3 % declare a data role (C01, SQ09).
* **Tiers.** T1 bio-declared core family; T2 ≥ 1 documented data project and ≥ 2 data repos, or a substantive project with ≥ 3 stars; T3 weak; T0 none. Generic ML/AI/data interest wording without a role noun is *adjacent* (1,038 accounts), not T1 (D-021).
* **Evidence strength.** mentioned (bio) < used (repo metadata/language) < demonstrated (README of a documented project) < project-demonstrated (and not educational); professional experience, language proficiency, years of experience, relocation intent and hiring outcomes are **not observable**. Git is true by construction and not counted.
* **Project** = owned non-fork data repository with README ≥ 300 chars, or ≥ 1 star, or a description; documented = README ≥ 1 k; substantive = documented and not course/tutorial work. Repositories ≠ projects.
* **Sources and quality.** GitHub REST API (B; AUP §7 research clause; no names/e-mails; raw private), Stack Overflow 2025 (B; ODbL; 410 AT respondents, ≈ 29 data roles), Eurostat (A; public raw). **LinkedIn members: never collected by member-site automation** (D-013/D-018). Private slot `src/acquisition/ingest_linkedin_manual.py` (templates in `data/raw/linkedin_supply/<date>/`, protocol docs/supply-methodology.md §7) with a channel-agnostic contract since D-026: each row names its `acquisition_method` (hand-coded `manual_ui`, or licensed exports such as `talent_insights`, `recruiter_export`, `licensed_vendor`); `FORBIDDEN_METHODS` (scrape, crawler, headless/browser automation, guest endpoint, jobspy, …) are rejected by the ingest. Contract: `docs/linkedin-slot-interface.md` (private). Manual cockpit `src/private/linkedin_coder/` (localhost, git-ignored) only records what the owner reads. The slot is still empty (2026-09-30). Kaggle not collected.
* **Precision.** Bio → family 78 % strict / 90 % lenient (SQ10); repository → project 75 % / 92.5 % (SQ11); README skill rules tightened (D-021). Every "any evidence" figure has a stricter "project-demonstrated" twin — quote both.
* **Files.** Private: `data/raw/github_supply/2026-09-17/`, `data/processed/supply_{candidates,projects,skill_evidence}.*`, review samples, Stack Overflow extract. Public: `outputs/tables/C01–C24, O01–O08, SQ01–SQ11, DS01–DS13`, figures BQ20–BQ26 and BQ36–BQ44 (legacy PNGs SF01, SF02, SF05–SF16 — S03/S04 retired — and DSF01–DSF08 are indexed in README → Legacy figure index), JSON `supply_*.json`, `demand_supply_*.json`, `project_evidence_map.json`, `operational_career_context.json`. Schema: `schemas/supply_schema.md`. Docs: supply-methodology, supply-findings, supply-data-quality, supply-research-audit, demand-supply-methodology, operational-career-intelligence, project-evidence-map, supply-completeness-audit, legal audit §10.
* **Interpretation rules.** Supply share ≠ workforce share; a missing public trace ≠ a missing skill (Power BI/Excel/SAP/SQL leave little code); bio/README language ≠ proficiency (99 % English); Styrian counts are complete for GitHub, Vienna counts are lower bounds; never rank or score individuals; no composite score exists; the demand side remains a one-day stock.

## 26. Visual decision layer (BQ01–BQ45, D-024, D-025)

**What it is.** 45 decision-bearing findings, each restated as a business question in the owner's terms, each answered by exactly one chart, each attached to the passage it answers. BQ01–BQ26 cover the market and the portfolio; BQ27–BQ33 cover the quality of the evidence itself (denominators, classification precision, sample sizes, source coverage, freshness, what a salary figure is, employer structure); BQ34–BQ45 close the gaps found by the question-coverage audit. Entry point for a human reader: `docs/visual-decision-board.md`. Machine-readable contract: `outputs/visual_questions.json` — for every figure the `question`, the `answer` (computed from the tables at render time, so it cannot drift), the `relationship` and `mark` from the GSD-DSX chart catalogue, the `tables` it is built from, the `units`, the `caveat`, the SHA-256 seal of the SVG and the documentation `anchors` it is embedded at.

**How an agent should use it.** To answer "what does the evidence say about X and where is it shown", read `outputs/visual_questions.json` first: it maps a decision question to the chart and to the source tables in one hop, without opening the documents. Quote the `answer` field rather than re-deriving a number from a figure, and carry the `caveat` with it. `outputs/figures/FIGURE-MANIFEST.yaml` is the same contract in DSX manifest form.

**Coverage and gaps.** `docs/question-coverage-audit.md` contrasts every question in the two original briefs with what the project can answer (VISUAL / TEXT / PARTIAL / OPEN). `docs/open-questions.md` is the register of questions that cannot be answered with the data held (24 entries as of 2026-09-30: 17 open, 4 structural, 1 will-not-do, 2 closed — OQ-14 by D-030, OQ-19 by D-027), each with the missing evidence, a closing path and a barrier class (effort / technical / contractual / regulatory / structural). **An agent asked a question this project cannot answer should quote the OQ entry rather than reaching for the nearest adjacent number.** The three worth closing first are OQ-09 (taxonomy recall, never measured), OQ-02 (candidate language levels) and OQ-01 (application outcomes).

**One reading was corrected by D-025.** `T09d_salary_by_skill.csv` and BQ17 show the advertised floor of ads that *mention* a skill. BQ45 controls for role family, seniority and state and 14 of 16 of those premiums stop separating from zero — quote the two together, never T09d alone.

**What it may not be used for.** The figures add no data, no table and no conclusion; they are a presentation of Layers 1–3 and inherit every limitation of those layers (`docs/limitations.md`, `docs/demand-supply-methodology.md`). A chart never makes a share into a requirement, a snapshot into a flow, a supply share into a workforce share, or a correlation into a hiring outcome.

**Refresh.** After any re-run of the analysis layers: `python src/analysis/make_visual_layer.py` (renders and re-seals) → `python src/analysis/embed_figures.py` (re-writes the embedded blocks in place and fails on an unresolved anchor) → `python -m pytest tests/test_visual_layer.py -q`. Builders: `visual_questions_demand.py` and `visual_questions_supply.py` (BQ01–BQ26), `visual_questions_evidence.py` (BQ27–BQ33), `visual_questions_followup.py` (BQ34–BQ45), all in `src/analysis/`; a new finding gets a new builder in the module of its layer; never edit a figure block in a document by hand — it is regenerated.
